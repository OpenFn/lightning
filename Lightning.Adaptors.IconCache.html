    Lightning.Adaptors.IconCache (Lightning v2.19.0)

    View Source

    Stateless filesystem functions over the on-disk adaptor icon cache, rooted at Lightning.Adaptors.Config.icon_path/0.

    Disk layout:

    <Config.icon_path/0>/<source>/<name>/<shape>.<sha8>.<ext>

    where sha8 is the first 8 lowercase hex characters of the icon sha256 on the adaptor row. Partitioning by source means switching ADAPTORS_STRATEGY between restarts cannot serve :npm bytes for a row now resolved through :local, or the reverse. Putting the sha in the filename makes cached?/5 a plain existence check, and a node holding an earlier icon misses and refetches instead of serving it forever. write!/6 removes the superseded siblings for that shape.

    Concurrent first-request fetches are coalesced by Lightning.Adaptors.Store.icon/3, not here.

    path(source, name, shape, ext, sha256)

    @spec path(source(), name(), shape(), ext(), binary()) :: Path.t()

    Disk path for an icon. Nothing is created.

    name may contain a / (scoped npm packages like @openfn/language-foo); Path.join/1 preserves the slash so the scope becomes a real subdirectory.

    Raises ArgumentError on a name PackageName would reject. The Scheduler writes icons straight from a strategy's response, before the row reaches Lightning.Adaptors.Catalogue.Adaptor.changeset/2 and its name validation, so this is the only thing standing between a hostile registry entry and a write outside the cache root.

    write!(source, name, shape, ext, bytes, sha256)

    @spec write!(source(), name(), shape(), ext(), binary(), binary()) :: Path.t()

    Atomically write bytes for sha256 and return the path written.

    The write is staged in a sibling temp file and then renamed into place, so concurrent readers never observe a half-written file. Any superseded file for the same shape, whatever its extension or pre-sha naming, is removed first, so a rename never lands on a directory left empty by its own sweep.
